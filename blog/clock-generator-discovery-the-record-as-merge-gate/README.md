## The question

The generator weighs many clocks for each build and selects one. A change to the engine can move that choice on a sample in ways that no one meant. How do you see all of it in a pull request, and how do you stop a change that makes a clock worse?

The answer, in [issue 600](https://github.com/abucnasty/clock-generator/issues/600), was a generated record for each blast job and one property module, instead of hand pins in the generation tests.

## How it works

Every sample and fixture of the blast is a job. For each job, one small JSON file in [`clock-generator/record/`](https://github.com/abucnasty/clock-generator/tree/master/clock-generator/record) holds the clock the generator selects and every other clock it weighed: verdict, whether it holds, rate, window cycle time, wakeups, windows and a hash of the clock. The file is generated by the blast and never edited by hand.

The first record was committed on 5 November. It had 75 jobs, written from the blast of one commit of master. It has 86 jobs now: the samples as they are, the fixtures, and variants. A variant is a sample with the options a game recording or a test sets on it, such as belts backed up.

CI then does two things on every pull request that changes more than documentation.

1. It generates every job again and compares the result with the committed files, field by field. A difference fails with a table of job, field, before and after.
2. It sets the selected clock of every job against the record of the pull request's base. It fails when one got worse and its job is not named in the lines the pull request adds to [`MOVES.md`](https://github.com/abucnasty/clock-generator/blob/master/clock-generator/record/MOVES.md).

The record has no target, so "worse" is defined by its fields, on the selected clock:

| It is worse when | |
| --- | --- |
| The job failed to generate | before it generated |
| The verdict ranks lower | stable, then no recovery, then unstable |
| `holds` | went from true to false |
| `rate` | is lower |
| `wake_ups` | is higher |

The check is named "Rec summary". It is a required check of the rulesets of `master` and of the hotfix branches. So a record that moved without a file, a property problem, or an unnamed worse clock stops the merge.

One module holds the properties that must be true of every job's result. There are six, for example that every inserter has exactly one route, and that a clock gets the disturbance trials exactly when one copy alone holds its rate.

## What the record showed

The largest test was 0.29.0. The pull request that models belts lane by lane changed 86 of 88 record files: 84 moved, 2 were added, 2 removed and 1 renamed. Every moved job has a line in `MOVES.md` with its reason. Some are plain. On the automation science sample, a clock that lost swings on a shared lane was replaced, and wakeups went from 50.174 to 300.696 a minute. The line says why, so the move is accepted with its reason and does not slip in.

Moves can also show a gain that the game confirms. The entry for Coordinated Sources lists, for each job, the game's count next to the simulator's. On the accumulator sample the move was 889.072 to 696.44 wakeups a minute, with 696.5 in the game.

## What changed because of it

**The record lost a field that did not belong.** Every clock carried a hash of its text. The 0.28.0 release and the 0.28.1 release each moved the text hash of all 86 jobs, because the blueprint text carries the engine's version. On 14 November the record format became `clock-record-3`: a clock has no `text_sha256`. A change of a description, or a version bump, now moves no record file ([#749](https://github.com/abucnasty/clock-generator/pull/749)). The clock hash, which says what the combinators do, stays.

**The record took the glossary's word.** The record's key for the window cycle time was `period`. [#710](https://github.com/abucnasty/clock-generator/pull/710) renamed it `window_cycle_ticks`, in line with the glossary, and moved no selection.

**Each check has a place.** The contribution guide says where a check belongs. What the generator selects or computes for a sample is held by the record, so "a moved value is a changed file and a MOVES.md entry, not a hand-edited assertion".

## What is not known

The record covers 86 jobs. It cannot see a build that is not one of them. The loss-trial change in [the post on the cold start](../clock-generator-discovery-loss-trials-cold-start/README.md) says so in its own words: builds outside the record are not measured.
